# 24. MEETING VISIBILITY & ACCESS CONTROL — CORE REQUIREMENT

Har meeting create karte waqt host/admin ko meeting ka **Access Type** select karna hoga.

## 24.1 Meeting Access Types

### A. PRIVATE MEETING

Private meeting me sirf wahi users join kar sakenge jinke email address meeting create karte waqt add/invite kiye gaye hain.

Example:

```text
Meeting:
"Private Training Session"

Access:
PRIVATE

Invited Emails:
user1@gmail.com
user2@gmail.com
user3@gmail.com
```

Result:

```text
user1@gmail.com  → ✓ Can Join
user2@gmail.com  → ✓ Can Join
user3@gmail.com  → ✓ Can Join

other@gmail.com  → ✗ Cannot Join
```

Agar unauthorized user meeting link ke through join karne ki koshish karta hai:

```text
Access Denied
You are not invited to this meeting.
```

### Private Meeting Rules

* Email invitation mandatory
* Only invited email can join
* Meeting link alone is NOT sufficient
* Laravel server-side email validation karega
* User authentication required hogi
* Invited email aur logged-in account ka email match hona chahiye
* Host/admin invited users ko manage kar sakta hai
* Invite revoke bhi kiya ja sakta hai

# 24.2 PUBLIC MEETING

Public meeting me koi bhi user meeting link se join request bhej sakta hai.

Lekin user **directly meeting me enter nahi karega**.

Flow:

```text
User opens Meeting Link
        ↓
Login / User Identification
        ↓
Join Request
        ↓
Waiting / Approval Screen
        ↓
Host receives request
        ↓
Host Approves
        ↓
User enters Meeting
```

Host ke paas:

```text
Approve
Reject
Remove
```

options honge.

# 24.4 Public Meeting — Optional Approval Policy

Meeting creation ke waqt:

```text
Public Meeting
```

ke saath approval policy configurable hogi:

```text
Approval Required = ON/OFF
```

Agar:

```text
Public
Approval Required = ON
```

to host approval mandatory hai.

Agar future version me:

```text
Public
Approval Required = OFF
```

allow kiya jata hai, to authenticated/allowed users direct join kar sakenge.

**Default:** Approval Required = ON.

# 24.7 Server-Side Access Validation

Join API par Laravel complete access check karega.

Example:

```text
POST /api/v1/meetings/{meeting}/join
```

Laravel checks:

```text
1. Meeting exists?
2. Meeting active?
3. Meeting time valid?
4. User authenticated?
5. Meeting private/public?
6. If private → email invited?
7. If public → approval required?
8. If approval required → approved?
9. User blocked/removed?
10. User role/permission valid?
11. Meeting capacity available?
12. LiveKit permission valid?
```

Sab checks successful hone ke baad hi:

```text
LiveKit Token
```

generate hoga.

---

# 24.8 Important Security Rule

**LiveKit room ka URL/room name mil jana meeting access ke liye sufficient nahi hoga.**

User ko pehle Laravel authorization pass karna hoga.

Correct flow:

```text
Flutter/Web
     ↓
Laravel Join API
     ↓
Access Validation
     ↓
Permission Validation
     ↓
LiveKit Token Generate
     ↓
LiveKit Room
```

Direct unauthorized LiveKit access prevent kiya jayega through proper token/grant configuration.

# 24.9 Host Approval Realtime

Public meeting me join request host ko realtime milni chahiye.

Architecture:

```text
Participant
    ↓
Laravel
    ↓
Database
    ↓
Laravel Reverb
    ↓
Host
```

Host approve kare:

```text
Host
 ↓
Laravel Approve API
 ↓
Database Update
 ↓
Reverb Event
 ↓
Participant
 ↓
LiveKit Join Token
 ↓
Meeting
```

Isse page refresh ki requirement nahi hogi.

# 24.13 Integration With Meeting Feature Permissions

Privacy/access aur feature permissions independent but compatible honge.

Example:

```text
Meeting:
PRIVATE

Audio:
ON

Participant Mic:
OFF

Video:
OFF

Screen Share:
OFF

Chat:
ON
```

Result:

```text
Only invited users
        +
Only approved/authorized access
        +
Listen + Chat only
```

Another example:

```text
Meeting:
PUBLIC

Approval:
ON

Host Audio:
ON

Participant Mic:
OFF

Participant Video:
OFF

Screen Share:
OFF

Chat:
ON
```

Result:

```text
Anyone can request
        ↓
Host approves
        ↓
Participant joins
        ↓
Can listen + chat only
```
